01 — Overview

これは何か

まず全体像を掴むための要約です。

NeoFunctions は、Minecraft のバニラコマンド機構（.mcfunction と各種JSON定義）だけを使って構築された、大規模なオリジナルRPGシステムのデータパックです。職業（クラス）システム、ボス戦、独自次元・バイオーム、属性ダメージ、進捗を使った膨大な図鑑（モンスター図鑑）システムなど、MOD無しでは通常実現しないレベルの機能群が、すべて素のコマンドの組み合わせで実装されています。

README には次のように記されています。「新世界を構築する新奇な秩序。新たな世界の法則を記述し、君の頭に宿す常識を容易に再構築する。」——この一文の通り、コード自体もひとつの"法典"として、独自の命名規則・階層規約・実行順序のルールで秩序立てられています。本ドキュメントはその法典を、外部から読む人にも理解できる形で解きほぐすことを目的とします。

領域役割規模の目安
neofunctionゲームロジック本体（tick処理・スキル・アイテム・戦闘）mcfunction 約3,984 / loot_table 3,080
neoadvancement進捗(advancement)を「イベント発火」「真偽フラグ」「図鑑エントリ」として使うための専用名前空間advancement 約3,820

admin開発補助（VSCode拡張、クリーンアップスクリプト、Pythonツール）。配布物には含まれるがゲーム内では機能しない開発者専用領域mcfunction 160（ゲーム内非稼働）
02 — Architecture

全体構造：4つの領域に分けられた責務

neofunction:functions 配下は、tick処理の起点コメントで明言されている通り、4つのトップレベルフォルダに責務が分割されています。

functions/ ├─ asset/ # 常時処理しない「データベース」的機能。演出・GUI・召喚・音・称号など ├─ entity/ # 全エンティティ(@e)を毎tick処理。負荷「極大」 ├─ player/ # 全プレイヤー(@a)を毎tick処理。負荷「中」 └─ system/ # 進捗・クロック・スケジュール等、単一の管理役が行う処理。負荷「小」

出典: functions/tick.mcfunction ヘッダーコメント（原文ママ、要約）

この4分割は tick.mcfunction のヘッダーに明文化されている数少ない「アーキテクチャ規約」のひとつです。ノートPCのような非力な端末でも動くように、「毎tick全エンティティを舐める」処理をできるだけ避け、システム管理役や進捗イベントに処理を逃がすという設計思想が、フォルダ構成そのものに反映されています。

フォルダ起点となる実行者コメント上の負荷ラベル代表的な中身
system/固定UUIDの管理役エンティティ 1体小進捗イベント処理、初期化、クロック、ダメージ計算
player/@a（全プレイヤー）中職業スキル、ゲームモード制御、HUD表示
entity/@e（全エンティティ）極大スポーン初期化、常駐スキル、ボスAI、ゴミ掃除
asset/他フォルダから呼ばれる補助関数群—（常時実行しない）演出、UI、召喚テンプレ、対話、称号

名前空間マップ

NeoFunctions.zip ├─ pack.mcmeta # pack_format 26、.lnk等の除外フィルタ設定 ├─ README.md # ヘッダー規約・命名規則・導入方法を明文化 └─ data/ ├─ neofunction/ functions, advancements, loot_tables, item_modifiers, │ predicates, recipes, structures, tags, damage_type, worldgen ├─ neoadvancement/ advancements（大半）, functions（少数の補助） ├─ neodimension/ dimension, dimension_type, worldgen/biome ├─ minecraft/ tags/functions（#minecraft:tick, #minecraft:load）, │ loot_tables, trim_material/pattern の上書き └─ admin/ 開発ツール一式（VSCode拡張・整理スクリプト・PPTX資料）
03 — Execution Flow

実行フロー：エンジンの鼓動から末端の処理まで

Minecraft サーバーが持つ2つの標準フック（#minecraft:tick と #minecraft:load）を起点に、どのように処理が枝分かれしていくかを追います。

3-1. 起動時（load）とtick起点の全体像

Minecraftエンジン
サーバー起動 / ワールドロード / 毎tick
#minecraft:load
tags/functions/load.json
#minecraft:tick
tags/functions/tick.json
neofunction:load
neofunction:tick
system/tick
負荷:小
player/tick
負荷:中
entity/tick
負荷:極大

この3分岐は tick.mcfunction 内で明示的にコメントされたコストの順に並んでいます。entity/tick は「この階層は本当に超大事だから、最低限.spawnの階層構造を理解してから編集して」という注意書きが残されているほど、変更の影響範囲が広い領域です。

3-2. 起動シーケンス（load 〜 初期化）

ワールドを開いた直後は、すべての初期化を1tickで終わらせず、schedule ... <n>t replace を使って数十tickにわたり段階的に処理を展開します。番号プレフィックス（1_〜9_、99_）がそのまま実行順序を表す、暗黙のうちに一貫している規約です。

neofunction:load
ログイン正常化メッセージ + 世界の正常性確認をschedule
asset/event/log-in
1秒後：接続処理、音楽、称号、チュートリアル分岐
system/setting
初回ロード時：番号付き設定ファイルをscheduleで直列展開
1_gamerule_*
10t / 15t後
2_scoreboard
20t後：全スコアボード定義
3_scoreboard_set
30t後
4_team / 5_storage
40t / 50t後
system/clock/all_clock_start
60t後：常時タイマー群を起動

3-3. .neo ディスパッチャの連鎖（例：ナイト職のスキル発動まで）

末端の処理にたどり着くまで、各階層のフォルダに置かれた .neo.mcfunction（ハブ関数）が条件分岐しながらバケツリレーする構造になっています。以下は「毎tick処理 → プレイヤー処理 → 職業ディスパッチ → ナイト職固有処理」という実際の呼び出し連鎖です。

functions/tick
player/tick
SP(冀求力)を持つプレイヤーのみ次へ
player/job/.neo
習得済み進捗(neoskill/2xx)で職業を判定
player/job/knight/.neo
手持ち武器の種類で分岐
player/job/knight/weapon

この連鎖は README のヘッダー規約にある「>呼び出し元」「=自身のパス」を、各ファイルを開くだけで前後の接続を追える"手動リンクリスト"として機能させています。

04 — Design Patterns

発見された設計パターン

バニラコマンドという制約の多い環境の中で、繰り返し使われている実装上の工夫を10個抽出しました。

01

進捗(advancement)を使ったイベントバス

system/adv/*

Minecraft の進捗機能が持つ20種類以上のトリガー（recipe_crafted, player_interacted_with_entity, changed_dimension, tick など、ほぼ全種類）を、そのまま「イベントの種類カタログ」として転用しています。仕組みは共通で、①条件を満たすと進捗が達成される → ②rewards.function で処理関数が呼ばれる → ③処理関数の最後で自分自身の進捗を revoke して未達成状態に戻す、という3ステップです。これにより同じイベントを何度でも発火できる、事実上の on(event) → handler() → reset() という一般的なイベント駆動モデルが、バニラ機能だけで再現されています。

# advancements/tick/.neo.json（発火条件：アドベンチャーモードでない）
"trigger": "minecraft:tick",
"rewards": { "function": "neofunction:system/adv/tick/.neo" }

# functions/system/adv/tick/.neo.mcfunction（処理本体）
advancement revoke @s only neofunction:tick/.neo   # 再発火のために自己剥奪
execute if entity @s[tag=argonaute] run return 0
tag @s[tag=!sur] add sur
02

.neo ハブ&スポーク・ディスパッチャ

全域（60箇所以上）

意味のあるフォルダには必ずといっていいほど .neo.mcfunction（あるいは .neo.json）という"そのフォルダの入口"が置かれ、タグ・スコア・進捗・所持アイテムなどの条件でさらに下位の関数へ振り分けます。ソフトウェアでいう index ファイルやルーターに相当し、フォルダ名を見ただけで「ここに来れば適切な分岐先へ飛ばしてくれる」という一貫した期待を持てる設計です。

03

タグによる有限状態機械

entity/*, player/*

エンティティ／プレイヤーの状態は変数ではなくタグの有無で表現されます。check（初期化済み）、vanilla（カスタム対象外）、boss、del（削除予約）、marked、sur（サバイバル領域）、fly0/fly1/downer/upper（挙動モード）など、タグの組み合わせがそのままオブジェクトの状態を表す簡易ステートマシンとして機能しています。

04

return run による早期リターン

分岐処理全般

execute if ... run return run function ... という形が繰り返し使われます。これは「条件を満たしたら関数を呼び、その戻り値を伴って即座に自分の処理を終える」という、一般的なプログラミング言語の if (cond) return handler(); に相当する制御構造で、続く行を評価させない早期リターンのイディオムとして機能します。player/job/.neo で6職業を順番に判定する処理がその典型例です。

05

番号プレフィックス + 段階的schedule

system/setting/*

1_gamerule→2_scoreboard→…→99_scoreboard_set_player のように連番でファイルを命名し、schedule function ... Nt replace でtickをずらしながら順番に実行します。重い初期化処理を1tickに集中させず、負荷を時間方向に分散させる工夫です。

06

固定UUIDのシングルトン管理役

0-0-0-0-1（66箇所で参照）

UUIDを 0-0-0-0-1 に固定した1体のarmor_stand（案内役NPC「カイ／χ」）が、①execute as 0-0-0-0-1 によるグローバル管理役（シングルトンオブジェクト）としての役割と、②tellraw の発言者としての物語上の案内NPCとしての役割を、同じエンティティで兼務しています。技術的な仕組みと世界観の演出を1つの実体に統合した効率的な設計です。

07

進捗番号帯による職業(enum)管理

neoadvancement:neoskill/2xx

職業は neoskill/200=ナイト、210=アリア、220=シューター、230=テイマー、240=ドクター、250=アサシンという十の位の帯で区切られ、各職業のサブスキルは 220〜229 のように一の位で管理されます。プログラミング言語の enum の値域割り当てに相当する、進捗IDの名前空間設計です。

08

スコアボード = RPGステータスDB

system/setting/2_scoreboard

スコアボードの目標(objective)を実質的なプレイヤーDBのカラムとして使用します。EXP（経験値）、LVL（レベル）、HP／HPmax、SP／SPmax（冀求力＝MPに相当）、CT（クールタイム）、DEF、MiningSpeed などが定義され、コメントには SPD・ATK・INT・RES・LUK・CRT という未実装のまま無効化されたステータスも残されており、設計時点での構想の広さと実装の現実的な取捨選択が同時に読み取れます。

09

属性ダメージシステムと新旧2つの実装の共存

damage_type/*, system/dmg/*

fire・aqua・wind・alternate というカスタムダメージタイプ（exhaustionやeffectsをJSONで定義）に対し、ダメージ処理は2系統が混在します。旧来方式は system/dmg/fire/1・10・100…のように数値を桁ごとの固定関数に分解して呼び出す方式、新しい方式は1.20.2以降のマクロ機能（$(atk)）を使って可変長引数を直接渡す方式です。マクロ機能導入前後の技術移行の過渡期であることがコードから見て取れます。

10

遅延ガベージコレクション

entity/skill/del

不要になったエンティティは即座に kill せず、まず del タグを付与し、翌tickにまとめて entity/tick から呼ばれる entity/skill/del が体力0化・ドロップ無効化などのNBT変更を行ってから kill します。死亡演出や召喚獣の後処理を安全に挟み込むための、削除を1tick遅延させるGC的パターンです。

05 — Explicit Conventions

明示されている規約

README.md に文章として明記され、専用のVSCode拡張機能（mcfunction-header）まで用意して徹底されているルール群です。

5-1. ヘッダーコメント統一フォーマット

対象の .mcfunction ファイル冒頭には、以下の順序・書式でヘッダーを揃えるというルールが定義されています。

# 命名：名称などあればこちらに移動して記載
# 説明：一行程度の軽いまとめ（複数ある場合は行を分けたまま残し、無理に1行へ結合しない）
# 実行条件：（あれば記載。複数あれば複数行のまま）
# >呼び出し元（自身のパスの一段上。複数ある場合は1行ずつ改行して列挙）
# =自身のパス（必ず最後の行。/function neofunction:〜 の形式で統一）
  • 命名：元のヘッダーに「命名」「名称」の記載があればそれを採用。無ければファイル名（拡張子抜き）から生成する。
  • 説明：「説明」「内容：」ラベル付き行、およびラベルの無い素のコメント行はすべて「説明」として扱う。複数行あっても結合せず # 説明： を複数行のまま残す。
  • 実行条件：元の「実行条件」ラベルの内容をそのまま保持し、説明の下・呼び出し元の上に配置する。
  • >（呼び出し元）：「呼び出し元」「呼出」ラベルや行頭 > の内容を集約。/function が付いていなければ付与して正規化。複数ある場合は1呼び出しにつき1行。呼び出し元が無ければ # > のみ残す。
  • =（自身のパス）：元の記載は信頼せず、実際のファイル格納場所（ディレクトリ構造）から機械的に再計算する。ヘッダーの一番下に必ず配置。
  • ヘッダーブロックの判定：ファイル先頭から # で始まる行が連続する区間とし、空行に達したら終了する（以降の本文中のコメントには触れない）。

このアルゴリズムがそのまま専用のVSCode拡張（mcfunction-header）としてツール化されている点が重要です。つまりこの規約は"努力目標"ではなく、ツールで機械的に強制される規約として運用されています。

5-2. 命名規則

README「その他」節に、共同開発時の見やすさを優先した命名の優先順位が明記されています。

  • 大文字はできるだけ使わない：ファイル名・識別子は基本的に小文字。
  • 命名の優先順位：①番号（ナンバー）を基本とする → ②必要なら小文字の省略語 → ③どうしても必要な場合のみ「型変数」的な CamelCase（先頭大文字＋単語区切りごとに大文字）を使う。
  • 命名はスプレッドシート管理：共同開発での見通しの良さを重視し、命名の割り当てはスプレッドシートで一元管理する運用。
  • \nのようなエスケープ改行は使わない：コマンド1行＝1命令という制約上、改行の必要な表現は素直に行を分けて書く、という趣旨の注意書きがある。

5-3. pack.mcmeta によるフィルタ規約

filter.block で .lnkファイル、neofunction:functions/info.lnk、minecraft:advancements/* を配布パッケージから除外する設定が明示されています。.lnk はWindowsのショートカットファイルで、開発環境内の補助リンクがビルド時に紛れ込まないようにする防御的な設定です。

06 — Implicit Conventions

暗黙のうちに守られている規約

README には書かれていないものの、コードを横断的に読むことで見えてくる、一貫して守られている（あるいは守られつつある）作法です。

  • ドット始まりの名前 = 内部ディスパッチャ／要注意領域
    .neo・.spawn・.all_trigger_make のように先頭にドットを持つファイル／フォルダは、そのフォルダの制御ロジックの中枢であり、他の一般ファイルより変更の影響範囲が大きい領域として扱われています。entity/tick.mcfunction のコメントで「.spawnの階層構造を理解してから編集して」と名指しで注意喚起されているのがその証拠です。
  • フォルダ＝責務、コメント＝負荷ラベル
    「asset/entity/player/system」という4分割そのものに加え、各起点コメントに「負荷（小）／（中）／（極大）」という定性的なコストラベルが書き添えられており、パフォーマンスへの配慮がドキュメントの一部として一貫して残されています。
  • 取り消し線的コメントアウトが設計変遷の記録として残る
    system/setting/2_scoreboard.mcfunction の SPD・ATK などの未実装ステータスや、entity/skill/.neo 内の一部旧処理のように、無効化されたコードがそのまま「将来やるかもしれないことのメモ」として残されています。削除せず残すことが、暗黙のうちにこのプロジェクトの流儀になっています。
  • 開発者の疑問・愚痴・TODOがコメントに直接書かれる
    system/scoreboard/add.mcfunction には「マルチプレイでこの処理をどう実装する？」という設計上の問いかけがそのまま残り、system/setting/2_scoreboard.mcfunction には「命名制限と命名法則がクソ」という率直な感想が残っています。コメントが単なる説明ではなく、開発者間の意思疎通ログとして機能しています。
  • 改行コードはCRLFが主流だが、新しいファイルはLFに移行しつつある
    調査したところ .mcfunction 4,167ファイル中 2,930ファイル（約70%）がCRLF、残りがLFでした。entity/tick.mcfunction など更新日時の新しいファイルはLFになっており、開発環境（エディタ／OS）の変遷が改行コードの混在という形で履歴に残っています。
  • # と ## の緩やかな使い分け
    ヘッダー部は単一の #、本文内の区切り（「内容」「再使用のために〜」など）には ## を使う例が散見されますが、厳密なルールではなく執筆者依存の緩い慣習にとどまっています。
  • 数字ID＋接尾辞という命名で"版"を管理
    system/dmg/fire/1・10・100のように、数値そのものをファイル名にする命名が随所に見られ、README の「基本ナンバー」方針が実装レベルでも徹底されています。

強み

徹底したヘッダー規約とツール化

全ファイルの88%以上が統一ヘッダーを持ち、専用VSCode拡張で機械的に強制されている。バニラコマンドという「関数シグネチャもドキュメンテーションコメントも標準機能では持てない」環境で、擬似的なドキュメンテーションレイヤーを自前で作り上げている。

責務分離が明確

asset/entity/player/systemという4分割と、それぞれの負荷ラベルが一貫しており、新規参加者でも「これは誰が毎tick実行するコードか」が推測しやすい。

パフォーマンスへの継続的な配慮

初期化処理のscheduleによる段階展開、entityループでの早期分岐（fly1/downer/upper/boss以外は即座に軽量パスへ抜ける)、64m制限タグへの受け渡しなど、随所に負荷分散の工夫がある。

拡張性の高いID設計

職業の進捗番号帯（200/210/220…）やダメージタイプの桁分割など、後から要素を追加しやすい名前空間設計になっている。

技術的負債・気になる点

実装方式の二重化

ダメージ計算に「桁分解の固定関数群（旧）」と「マクロ関数（新）」が併存している。1.20.2以降のマクロ機能への全面移行が完了していない過渡期状態。

未実装ステータスの放置

SPD・ATK・INT・RES・LUK・CRTがコメントアウトされたまま残っており、当初設計と現在の実装に乖離がある。将来これらを追加する際、既存のスコアボード命名との衝突リスクがある。

改行コードの混在

CRLFとLFが約7:3で混在しており、複数の編集環境（時期）を経てきたことがうかがえる。差分管理（Git等）を行う場合はノイズの原因になりやすい。

最大12階層のネスト

system/adv/tick/cmd/offhand/994/dim/ceresta/objective.mcfunctionのように深いパスが存在し、規約通りに書けば毎回ヘッダーの=行が長くなる。可読性とパスの追跡コストはやや高い。

グローバルな単一名前空間のリスク

スコアボード目標もタグも進捗IDも、Minecraft側にnamespace分離の仕組みが乏しいため、4,000以上のファイルを横断する規模になると命名衝突のリスクが構造的に残る（スプレッドシート管理という運用でカバーしている）。

09 — Reading Guide

はじめて読む人への実践ガイド

4,000以上のファイルを前から読む必要はありません。以下の順番で"入口"だけ押さえれば全体像がつかめます。

① 起点の2ファイルを読む

functions/load.mcfunction と functions/tick.mcfunction。すべての処理はここから枝分かれするので、まずこの2つのヘッダーコメントだけで全体方針を把握できます。

② 気になる機能名で .neo を検索

「ジョブを見たい」なら player/job/.neo、「ボスを見たい」なら entity/skill/boss/.neoというように、フォルダ名から.neoファイルを直接開けば、その領域の分岐ロジックだけを短時間で把握できます。

③ ヘッダーの > と = を手掛かりに前後をたどる

各ファイルの >呼び出し元を見れば「誰から呼ばれているか」を、=自身のパスで全文検索すれば「自分がどこから参照されているか」を機械的に逆引きできます。

④ 進捗JSONは「イベント登録」として読む

system/adv/配下のトリガー名（recipe_crafted等）がそのままイベント名です。対応するadvancements/側のJSONで発火条件を、functions/側の.neoで処理内容を読めば、1つの機能の入出力がセットで理解できます。

この解析は約4,167本の.mcfunctionと8,040本のJSONのうち、代表的なファイル・パターンを横断的に抽出して構成したものです。全ての葉ファイルを網羅したものではなく、「どう読めば全体像に迷わずたどり着けるか」という設計思想・骨格の解説を目的としています。
