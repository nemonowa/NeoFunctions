NeoFunctions
コードの流れと規約の解説書

Minecraft 1.20.4 用データパック「NeoFunctions」（作者 argonaute_nemo / SoraFlete）を、ファイル構造・実行フロー・データ設計・コード規約の4つの視点から読み解いた資料です。データパックを触ったことがない人でも順に読めば「どこで何が起きるか」が追えるように書いています。

12,333ファイル総数（約70MB）
4,167.mcfunction（コマンド群）
8,040.json（進捗・ルート等）
100%ヘッダー規約の準拠率

1. 全体像 — 「進捗をイベント、タグを型、スコアを変数」として使う設計

まずこの3つの置き換えを掴むと、以降のすべてが読めます。

Minecraft のデータパックには「関数」「進捗（advancement）」「ルートテーブル」「述語（predicate）」といった素材しかなく、if 文もイベントリスナーもクラスもありません。NeoFunctions はこれらを次のように"流用"して、RPG（レベル・職業・スキル・ボス・クエスト・ダンジョン・独自次元）を丸ごと構築しています。

3.2 スポーン検知パイプライン（entity/.spawn/.neo）

すべてのエンティティは生成直後の1tickだけ「未検査（tag=!check）」の状態で存在します。この1tickで分類を済ませ、check を付けて二度と通さない、という"入国審査"の設計です。

3.3 タグ駆動の常時スキル（entity/skill/.neo → .neo-1）

毎tick @e[tag=!vanilla,tag=check]、つまり「何かしらカスタムなエンティティ」だけがこの階層に入ります。中身は二段階のふるいで、重要度と距離で処理を絞っています。

  1. .neo（最重要層） — fly1（奈落復帰）、downer/upper（親子の生存連動削除）、fly0（接地削除）、boss のどれにも該当しなければ即 .neo-1 へ return。これらは距離に関係なく常時追跡が必要なもの。
  2. .neo-1（64m 制限層） — 認識タグ（air, leader, roll, fly2/3, look, beacon, protector, lava_fishing, superdisplay, aj.global.root…）のどれも持たなければ vanilla を付けて以後除外。さらに「64m 以内にプレイヤーがいなければ return 0」。以降は各タグごとに子関数へ委譲。

暗黙ルール： 新しい常時スキルタグを追加するときは .neo-1 冒頭の「該当しなければ vanilla」の長い execute if entity @s[tag=!…] にも必ず追記しないと、そのエンティティは翌tickに vanilla 扱いになり、二度と処理されません。ヘッダーの「ここのコマンド数をむやみに増やすな！丁寧に子関数に逃がせ」も同じ階層への注意書きです。

削除は直接 kill せず、必ず tag @s add del → 次tickの skill/del で「Health:0, DeathLootTable:"empty", Silent, DropItem:0b をマージしてから kill」します。ドロップ・音・死亡ルートを確実に無効化するための一段遅延の削除規約です。周期削除用に del1s del10s del300s del1200s タグも用意されています。

4.1 .clock 親進捗によるクールダウン

Minecraft の進捗は親が達成されていないと子は判定されないため、これを利用して「発火頻度」を作っています。advancements/.clock/how.txt に作者自身がメモを残しています。

4.2 検知 → 関数 → 再装填 のワンセット

# advancements/player_killed_entity/1010.json（検知）
{ "parent": "neofunction:.clock/5s",
  "criteria": { "requirement": { "trigger": "minecraft:player_killed_entity",
     "conditions": { "player": [{ "condition": "minecraft:entity_properties", "entity": "this",
        "predicate": { "equipment": { "head": {"nbt":"{CustomModelData:1010}"}, "chest": {"nbt":"{CustomModelData:1011}"}, ... }}}]}}},
  "rewards": { "function": "neofunction:system/adv/player_killed_entity/1010" } }

# functions/system/adv/player_killed_entity/1010.mcfunction（処理）
# 命名：1010
# 説明：進捗達成時
# >/advancement neofunction:player_killed_entity/1010
# =/function neofunction:system/adv/player_killed_entity/1010
title @s actionbar {"text":"🔯セットスペル発動【苺甲鎧】",...}
playsound minecraft:block.sweet_berry_bush.pick_berries record @s ~ ~ ~ 1 1.5 1
loot give @s loot neofunction:item/317

規約として「進捗のパス」＝「関数のパス」が完全に対応します（advancements/X/N.json ↔ functions/system/adv/X/N.mcfunction）。再装填（revoke）は .clock 親に任せるため、個別の処理側には revoke が書かれません。例外は tick/entity_scores/* 系で、こちらは処理側で自分自身を advancement revoke @s only … します（trigger 系など「1回きり」の意味を持つため）。

4.3 被弾相手の特定 — UUID を進捗で二進展開する

player_hurt_entity 進捗は「誰を殴ったか」を関数に渡せません。NeoFunctions はこれを、エンティティの UUID[0] を 31 個の判定用進捗条件に分解して照合するという力技で解決しています。

  1. スポーン時 uuidcheck：UUID[0] を符号と 2^30〜2^0 のビットに分解し、該当ビットのタグ UUID30…UUID0, UUID- を付与（asset/nbt/for マクロでループ）。
  2. 各 player_hurt_entity/N.json には主条件 requirement の他に、犠牲者のタグ UUID30…を個別に見る 31 個の criteria（名前 "30"〜"0", "-"）が並ぶ。
  3. 処理側は .get_entity {Name:"N"} マクロを呼び、「達成された criteria の組み合わせと一致するタグを持つモブ」だけを tag hit として残す。
  4. 処理後 tag @e[tag=hit] remove hit で片付ける。

この方式は 1.20.4 時点で「攻撃対象を確実に取る」ほぼ唯一の手法です。代償として player_hurt_entity/*.json が肥大化し、tag=hit／tag=attacker が一時状態タグとして多数の関数に散らばります（hit 119箇所、attacker 114箇所）。

5. ロード・ログイン・初期化の状態遷移

「即読み込むと検知できないため分離」— リログ直後はチャンクもエンティティも未読込なので、すべて schedule で遅延させる。

0-0-0-0-1 とは： UUID 00000000-0000-0000-0000-000000000001 を固定で持つシステム用エンティティ。nexus 次元 (1280,128,1280) 付近に常駐し、system/tick で毎tick回転させることで「生きているか」が観測でき、ワールド共有の LVL/DEF スコアの持ち主にも使われます。ワールドの"心臓"なので、不在ならログインチェックが再召喚します。

7. ID 体系とアセット — 「番号ひとつで全部つながる」

「スプレッドシートのマクロで出力したデータを貼り付けるだけで全てが叶う」（3_item_to_summon のコメント）

README の命名規則にある「基本ナンバー」の意味がここです。アイテム・エンティティ・スキルはそれぞれ整数 ID を持ち、同じ番号のファイルが複数の場所に置かれることで、関数・ルート・図鑑・検知が自動的に対応します。ファイル名の 2,235 個（54%）が純粋な数字なのはこのためです。

ID の予約域（観測から推定）

  • CustomModelData は 0〜1847 をほぼ連番で使用。-2, -3, -33, 995〜999 付近はシステム用（HP 表示・目標表示・GUI 部品）。
  • 4桁の 1010〜1013 のように連番4つで「防具セット（頭・胴・脚・足）」を表す。セット揃い判定は player_killed_entity/1010.json のように先頭 ID で代表する。
  • 職業スキルは neoskill/200,210,220,230,240,250 が根、その後ろが各職業のツリー。
  • trigger の code 値も番号空間：1〜16 汎用、20番台＝星屑交換、61番台＝スキルスロット、1234567890/20210516 は隠しコード。

10. 規約 — 明文化されたものと、コードから読み取れる暗黙のもの

明示README や関数ヘッダーに文章で書かれている　暗黙書かれていないが全ファイルが従っている（破ると壊れる）

10.1 明文化された規約

明示R1. 関数ヘッダーは5行構造で固定（README「ヘッダー統一プロンプト」）

# 命名：名称（無ければファイル名から生成）
# 説明：1行程度。複数あれば「# 説明：」を複数行（無理に結合しない）
# 実行条件：（あれば。説明の下・呼び出し元の上）
# >/function 呼び出し元（複数なら1行ずつ。無ければ「# >」だけ残す）
# =/function neofunction:自身のパス（必ず最後の行・ディレクトリから機械的に再計算）
（空行で終了。以降の「# 内容」等の本文コメントはヘッダーに含めない）

実測　4,167ファイル全てに「命名」と末尾「=/function」がある（100%）。「>」は4,141（99.4%）、「実行条件」は257。8ファイルが「(呼び出し元が見つかりませんでした)」と自動生成の痕跡を残す。「=」パスと実際の格納場所の不一致は0件。admin/mcfunction-header-0_4_0.vsix という自作 VSCode 拡張で機械的に整形していると推定される。

明示R2. ファイル名は小文字・番号優先（README「その他」）

「ファイルの命名はできるだけ大文字を使わないでね。基本ナンバー、必要なら小文字省略語、どうしてもの時は型変数（CamelCase）」。

実測　大文字を含む .mcfunction ファイル名は 0件。純数字ファイル名 2,235件。省略語例：cmd（CustomModelData）、adv、aec、csgui、lvl、sp。CamelCase はタグ名側に逃がされている（LTPivot, FrogBoss, MusicStop, UUIDchecked）。

明示R3. 本文は「# 内容」から始め、ヘッダーとの間に空行2行

実測　1,803ファイルに「内容」見出し。表記ゆれあり：# 内容／## 内容／#内容／## 内容：。

明示R4. 階層ごとの負荷ルール（tick.mcfunction, entity/tick, entity/skill/.neo-1）

  • system（1体起点）→ player（@a）→ entity（@e）の順に呼ぶ。@e 層は「重い！減らせ！！！」。
  • 「進捗やクロック処理はシステム階層に、常時処理を使用しないデータベースはアセット階層に」。
  • 「ここのコマンド数をむやみに増やすな！丁寧に子関数に逃がせ」（.neo-1）。
  • エフェクト検知（nbt={active_effects…} を @e に）は「超オモイ！極力実装しません」とコメントアウト。

明示R5. 説明未記載は「（説明未記載）」と書く／誰かのためにコメントを遺す

出典　minecraft/tags/functions/tick.json の先頭コメント「コードはいつか読むかもしれない誰かのために適切にコメントを遺しましょう」。asset/summon/100 等に「（説明未記載）」プレースホルダ。

10.2 コードから読み取れる暗黙の規約

暗黙I1. ドットで始まるファイルは「階層の入口／内部専用」

.neo（77件）がそのフォルダのディスパッチャ。.macro .all .get_entity .spawn .clock .all_trigger_make など、直接呼ぶものではない補助関数・フォルダにドットを付ける。IDE で先頭に並ぶ副次効果もある。

暗黙I2. 進捗パス ＝ 処理関数パス

advancements/<trigger>/<id>.json の rewards.function は常に system/adv/<trigger>/<id>。トリガー名を変えずにフォルダ名にする。1件だけ tick/ 下に細分（cmd/csgui/quest/looking_at…）。

暗黙I3. 検知進捗は .clock/* を親にし、処理側で revoke しない

周期関数がまとめて revoke @a from .clock/Ns する。例外は「1回きり」の意味を持つ tick/entity_scores/* 系で、処理内で revoke @s only。

暗黙I4. 削除は kill ではなく tag del

次tickの skill/del が NBT を無害化してから kill。ドロップ・音・DeathLootTable を確実に殺す。周期版 del1s/10s/300s/1200s。

暗黙I5. 一時タグは同じ関数内で必ず外す

hit attacker looked interacted hooked resolve temp_display は「付ける → 使う → remove」を1関数で完結。残留すると次の検知で誤爆する。

暗黙I6. マクロは「N.mcfunction を $(key) で呼ぶ」薄い入口

asset/summon asset/item asset/skill は1行の $function …/$(summon)。引数名＝フォルダ名。ループは asset/nbt/for {Function,List} で汎用化。

暗黙I7. 早期 return によるガード節を先頭に固める

execute if entity @s[tag=!…] run return run …／execute at @s unless entity @a[distance=..64] run return 0。639ファイルが return を使用。ディスパッチャでは「該当しないものを先に弾く」が先。

暗黙I8. 偽プレイヤーの接頭辞

#Calc…＝計算用一時（表示されない）、$N const＝定数、%LTAngle＝数学ライブラリ（LT=LookAt/Pivot 系）、接頭辞なし小文字（night random froggame）＝機能フラグ。-1 が ON。

暗黙I9. 実行順を数字接頭辞で示す

setting/1_gamerule…5_storage、level/0_first_get_exp…3_lvl_up、.spawn/obj/item/3_item_to_summon…5_item_to_quest、ログイン検査 log-in/0..5（ErrorCode）。

暗黙I10. スコア objective には必ず日本語の表示名

「【耐久力】HP表示用」「【冀求力】Soul」。プレイヤーに見えるスコアは「【カテゴリ】説明」形式、内部用は「LevelSync 計算用(own)」のように用途を書く。

暗黙I11. 開発者向け通知は creative 限定 tellraw

tellraw @a[gamemode=creative] "Ready! > neofunction:…" を初期化関数の冒頭に置き、実行トレースにする。旧式処理には「注：旧式の処理です！」を creative へ出す。デバッグ表示は tag ad_info。

暗黙I12. 非表示にする値は numberformat blank

サイドバー装飾行 upper/downer/url は極端な値で並び順を固定し、display numberformat blank で数値を隠す。

暗黙I13. 「巨大な選択肢」はストレージ配列に持ち、関数を増やさない

改良型作業台のレシピは storage neofunction:crafter crafter_recipe に append。イースターや会話も storage:talk/main_story。

暗黙I14. 発火媒体は「バニラアイテム＋NBT」

紙・構造物ブロック・スポーンエッグ・花火の星・小麦を .spawn/obj/item で解釈し、NBT の summon/skill/quest キーで振り分ける。新機能を足すとき既存のアイテム ID を消費しない。

規約チェックリスト（新しい機能を追加するときに）

  1. ヘッダー5行を書く（最後は =/function 自パス）。呼び出し元を > に列挙。
  2. ID を採番し、item なら loot_tables/item/N＋neoadvancement:neoitem/N、entity なら asset/summon/N＋loot_tables/asset/summon/N＋neoentity/N を揃える。
  3. イベントで動くなら advancements/<trigger>/N.json（parent は .clock/*）＋ system/adv/<trigger>/N.mcfunction。
  4. 常時処理が要るなら tag を決め、entity/skill/.neo-1 の除外リストに必ず追記して子関数に逃がす。@e に nbt 判定を書かない。
  5. 一時タグは同じ関数で remove、削除は tag del。
  6. 新しいスコアは本当に「個体ごと・頻繁に変わる」か検討し、そうでなければ storage か偽プレイヤーへ。

11. 評価と改善提案

4年以上（2022/7〜）継続開発された個人〜少人数プロジェクトとして見た評価。

◎ 強み

  • ヘッダー規約の100%準拠とツール化。呼び出しグラフが grep だけで追える。
  • 起点の3本化＋負荷順序。tick 直下がほぼ関数呼び出しだけで、性能方針が構造に埋め込まれている。
  • ID 一元化。番号ひとつで関数・ルート・図鑑・検知が揃い、スプレッドシートから量産できる。
  • 自己修復するロード処理。壊れた箇所だけ直し、状態をチャットで報告する（ErrorCode 0〜5）。
  • マクロ・return・ストレージの1.20.2+機能を活用し、旧式の巨大 if 連鎖を減らしている（「旧式の処理です」の警告で移行中を明示）。
  • コメントに負債の自己申告（「いつか修正希望」「今後汎用処理に移動予定」）があり、放置ではなく認識されている。

△ リスク・負債

  • スキル除外リストの二重管理（.neo-1）。追記忘れが静かなバグになる。→ タグ一覧を1つの function tag か storage に集約する余地。
  • UUID 二進展開による player_hurt_entity/*.json の肥大化。1.21 系では damage.source_entity 側の改善やアイテムコンポーネント化で全面書き直しが必要。
  • 配布物に開発資材が同梱（.zip 36、.lnk 7、.pptx 2、.vsix 2、.py 3）。pack.mcmeta の filter は .lnk しか除外しない。→ ビルド時に除外。
  • 「内容」見出しや「説明」の表記ゆれ、assasin（assassin）などの綴り固定。修正はリネームコストが高いので用語集で吸収するのが現実的。
  • ハードコード座標（nexus 1280,128,1280 / 1286,130,1294 の command_block 検査）。ワールド生成条件が変わると初期化が壊れる。
  • 1秒クロックに @e nbt 判定（ネザースター検出）。作者も「ちょい重いかなぁ？」と認識。→ アイテムスポーン時の .spawn/obj/item 側で完結させる。
  • スコア objective 93個。予約済み未使用（ATK/INT/RES/LUK/CRT はコメントアウト）と、SPxxp のようなキャッシュ列が混在。

1.21 以降へ移植するときの当たり

  • CustomModelData（NBT）→ custom_model_data コンポーネント：進捗の "nbt":"{CustomModelData:N}" 約2,000箇所と loot の set_nbt 1,850件が影響。ID 体系自体は温存できる。
  • functions/ → function/、advancements/ → advancement/ 等の複数形廃止：ヘッダーの =/function neofunction: パスは名前空間パスなので影響なし。
  • DeathLootTable による種族判定は続行可能だが、図鑑の looking_at.nbt 検知は要確認。
